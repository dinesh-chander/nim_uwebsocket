## Response write/backpressure strategy

- Fetch-style response path (`RequestContext`):

  - Shared continuation helpers slice by `write_offset` and retry `tryEnd` in `src/bun.js/api/server/RequestContext.zig:866`.
  - Uses corked execution for combined header/body paths (`runCorkedWithType`) for sendfile and buffered response metadata writes in `src/bun.js/api/server/RequestContext.zig:1011` and `src/bun.js/api/server/RequestContext.zig:1095`.
  - Explicit HEAD logic writes metadata/length then `endWithoutBody` in `src/bun.js/api/server/RequestContext.zig:1422`.

- Stream/file response path:
  - Uses OS sendfile loop when available (non-SSL, non-Windows), with `onWritable` re-entry and `markNeedsMore()` in `src/bun.js/api/server/RequestContext.zig:787` and `src/bun.js/api/server/RequestContext.zig:846`.
  - Performs platform-specific file-type guards (macOS regular-file only, Linux regular/FIFO/socket) before sendfile in `src/bun.js/api/server/RequestContext.zig:945`.

- Node HTTP compatibility path (`NodeHTTPResponse`):
  - `write()`/`end()` funnel through `writeOrEnd(...)` in `src/bun.js/api/server/NodeHTTPResponse.zig:833`.
  - Backpressure semantics:
    - `raw_response.write(bytes)` returns `.want_more` or `.backpressure`.

## Concurrency and scaling model

- Primary HTTP execution appears single-event-loop per server instance:
  - Server binds to current async loop in `src/bun.js/api/server.zig:1804`.
  - No internal thread-worker fanout in these HTTP server files.

- Cross-process scaling knob is `reusePort`:
  - Config field in `src/bun.js/api/server/ServerConfig.zig:52`, mapped to uSockets listen options in `src/bun.js/api/server/ServerConfig.zig:314`.

## Transferable learnings for `nim_express` / `nim_usockets`

### P0

1. Standardize one backpressure contract across all response modes (`tryEnd + onWritable(offset)`).
2. Enforce early body-size rejection from `content-length` before buffering.
3. Keep sync path allocation-light; clone headers/url only on async transition.
4. Maintain aggressive request-context pooling with deterministic return.

### P1

1. Consolidate wildcard fallback registration by uncovered methods.
2. Preparse route param keys once; keep stable param-object shape for handlers.
3. Delay request-body buffer allocation until first chunk; cap prealloc.
4. Cork small static responses to reduce write syscall count.

### P2

1. Keep Date header as a periodically refreshed shared value.
2. Keep Node-compat behavior in isolated adapter layer so core path stays minimal.

## Risks/tradeoffs if adopted

1. Lifecycle complexity rises quickly (pooling + async refs + abort/timeout interactions).
2. Backpressure correctness bugs are subtle and hard to test exhaustively.
3. OS-specific sendfile behavior requires explicit platform branching.
4. Some optimization-friendly route constraints may reduce API flexibility.
5. `reusePort` defaults must be explicit/documented to avoid deployment surprises.
